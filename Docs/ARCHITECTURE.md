# EchoCave — Architecture

## Game summary

Grid puzzle. Tap a bat: it flies in its arrow direction until it leaves the board. If another bat blocks the path it bounces back and the move is spent. Each level has a move limit and 3 stars. Some bats are hidden ("in the shadow"); limited echo pings reveal their arrows for a few seconds.

## Layers and assemblies

```
EchoCave.Core    pure C# (noEngineReferences)   Board, Bat, MoveResolver, EchoService, level model, solver
EchoCave.Game    MonoBehaviours + presenters     bat views, board view, input, game flow states, composition root
EchoCave.UI      UI Toolkit views + presenters   HUD, popups (Complete/Pause), stars, ping button (D-016)
EchoCave.Ads     ad edge                         IAdService, providers (AdMob/MAX/null), rewarded flows
EchoCave.Tests   EditMode tests                  core logic, solver, services
Rokert.Core      external package (UPM)          ServiceLocator, EventBus, StateMachine, CommandHistory, ObjectPool
```

Dependency direction: `Game`, `UI`, `Ads` → `Core` → `Rokert.Core`. Core never references the others. Editor tooling (level editor + solver window) lives in an `EchoCave.Editor` assembly referencing Core.

## Core domain (pure C#)

- `Board`: width/height, bats by cell. No rendering concepts.
- `Bat`: id, cell, `Direction`, `IsHidden`.
- `MoveResolver`: given board + tapped bat, returns a `MoveResult` (Exited / Bounced with the blocking bat and stop cell). Deterministic; no side effects until applied.
- `EchoService`: ping budget and the temporary reveal of hidden bats (D-018). `TryPing(board)` returns a `PingResult` and spends a ping only when it starts a reveal; `Tick(deltaSeconds)` runs the reveal timer, so the core owns no clock; `GrantPings` adds pings (rewarded ads). The board is never mutated: a revealed bat is only listed in the service (`IsRevealed(id)`), so undo and the solver are unaffected. A view shows a bat's arrow when `!bat.IsHidden || echo.IsRevealed(bat.Id)`. Notifies through C# events `Pinged` and `Expired`; the adapter to the `EventBus` lives in `Game` (ROK-147).
- `IEchoStrategy` / `EchoPulse`: what a ping reveals (bat ids) and for how long. `RevealAllHiddenStrategy` is the default; its duration is a constructor argument, supplied from a ScriptableObject by the composition root.
- Level data model: plain classes loaded from ScriptableObject/JSON by an adapter in `Game`.

## Presentation (MVP)

- **View** (MonoBehaviour): draws and forwards input events. No decisions.
- **Presenter**: subscribes to the view, calls the core, updates the view. Plain C# class where possible.
- `GridLayout2D` (`EchoCave.Game`): maps cells to world positions and back. Board centered on the origin, Y up like `Direction`. Views and input share it so no view does coordinate math.
- `BatView`: bat sprite + arrow overlay, or a dark "?" silhouette when hidden. Animations use DOTween (D-014). `ResetForPool` kills its tweens and restores the prefab pose. A hidden bat holds one blend value (0 silhouette, 1 bat) and cross-fades between them with a small pop (`Reveal(delay, fade, pop)` and `Conceal(fade)`); `SetRevealed(bool)` and `SetHidden` stay immediate.
- `BatFactory`: plain C# over `ObjectPool<BatView>`. `Get(Bat)` returns an active, bound view; `Release` and `ReleaseAll` recycle them. It tracks active views because the pool accepts a double release. Views are children of a container, which is what frees them: the pool drops items it cannot keep without destroying them. The board view builds it from a serialized prefab and container.
- `BoardView`: draws the core board and plays move animations with DOTween. `Build(Board)` replaces the scene, `Play(MoveResult, onComplete)` animates one tap (fly-out and recycle, or fly, bump, knock the blocker and return). It decides nothing; the presenter passes it the result the core already produced. Positions are local to its transform.
- `IBoardView`: the slice of the board view the presenter and the flow use (`Build`, `Clear`, `TryGetCell`, `Play`, `SetRevealed`, `ShowPing`, `ShowRejected`), so their tests run against a fake. `SetRevealed(ids)` shows exactly those hidden bats as revealed with a fade and no wave (the echo running out, a loss; `BatView` remembers whether it is hidden by default); `ShowPing(ids)` is what an accepted ping calls: it plays the wave and reveals each listed bat when the ring reaches it (D-028); `ShowRejected` shakes the bats to say "that did nothing".
- `BoardPresenter`: plain C#. `HandleTap(world)` maps the point to a cell through the view, and a tap on a bat becomes a `MoveCommand` run through `CommandHistory`; the view then animates `command.Result`. Taps are ignored while an animation plays (D-015). `Start()` builds the view and clears the busy flag.
- `TapInput`: MonoBehaviour with a code-defined `<Pointer>/press` action (mouse, pen, touch; no input actions asset). Raises `Tapped(worldPoint)` and nothing else.
- `LevelRules` (Core): `Evaluate(session, level)` returns `InProgress`, `Won` or `Lost`. Won = board empty; Lost = move limit used up with bats left; Won is checked first (D-017).
- `GameFlow` (plain C#): owns a `StateMachine<FlowState>` with Menu, Playing, Won and Lost, the current level index, and the session and presenter of the level being played (a new pair per attempt, so undo history never leaks between attempts). The player's intents (`RequestPlay`, `RequestRetry`, `RequestNext`, `RequestMenu`) set a flag only when they make sense in the current state; transitions consume it on the next `Tick`, and every state change clears the flags. Playing waits for the presenter to be idle before it goes to Won or Lost. Publishes `LevelStarted` (with the ping budget), `LevelWon`, `LevelLost`, `PingUsed`, `EchoExpired` and `PingRefused` (readonly structs) on the `EventBus`. It also owns the echo of the attempt (D-019): one `EchoService` per attempt, ticked only while Playing (`Tick(deltaSeconds)`); `RequestPing()` acts at once and only while Playing, and a refused ping publishes `PingRefused` and calls `ShowRejected`; losing reveals every hidden bat so the player sees the mistake. It also owns the pause (D-021): `IsPaused` with `RequestPause` / `RequestResume`, only while Playing; a pause blocks taps and pings, freezes the echo clock and defers Won and Lost, and retry or the menu end it. `MoveSpent`, `PauseChanged` and `MenuOpened` complete the events the HUD listens to.
- `FlowState` and its four subclasses: only react to `Enter`; the rules live in `GameFlow`.
- `LevelCatalog` (ScriptableObject): the levels in play order, handed to the flow as `LevelDefinition`s.
- `EchoSettings` (ScriptableObject): the reveal duration. `GameRoot` turns it into the `RevealAllHiddenStrategy` the flow receives.
- **Edge services** (`Game/Services`, D-027): `ISaveService` keeps `PlayerProgress` (Core, pure: best stars and fewest moves per stable level id, D-029; a win never lowers either). `SaveService` loads from an `ISaveStore` when created and writes whenever a win improves something or an audio switch changes (the save holds the sound and music switches too, D-031, and the hint count, D-032; `GameRoot` copies them into the audio service at start and the pause popup starts from them); `PlayerPrefsSaveStore` is the real store (IndexedDB on WebGL, app storage on Android), `InMemorySaveStore` serves tests. `SaveSerializer` (JSON, versioned) never throws on a bad save: it reports it and the game starts fresh. `IAudioService` / `NullAudioService` only remember the two switches until ROK-173; `IAnalyticsService` / `NullAnalyticsService` count nothing. `ProgressRecorder` (plain C#, created on enable and disposed on disable by `GameRoot`) listens to `LevelWon` (translating catalog position to level id) and `AudioToggled` on the EventBus. `LevelData.levelId` is validated by `GameRoot` through `LevelIdRules`; the generation runner assigns ids to levels that lack one. Nothing reads the progress yet; `EchoCave > Save > Log progress` and `Delete progress` let you inspect and wipe it in the editor.
- **Audio** (`Game/Audio`, `Game/Services`, D-030): `IAudioService.Play(SoundCue)` is the one door. `AudioService` (plain C#) forwards a cue to an `ISoundOutput` unless the sound switch is off; `SoundPlayer` (MonoBehaviour in the scene) is the output: a small pool of `AudioSource`s, with `VoicePicker` choosing the voice (first idle one, else the oldest is cut) and `SoundThrottle` limiting how often a cue may fire. `SoundBank` (ScriptableObject) maps each `SoundCue` to a clip, a volume and a minimum interval; `FindProblems()` and `ShippedSoundsTests` catch a missing clip. `SoundCuePlayer` (plain C#, like `ProgressRecorder`) turns EventBus events into cues: `PingUsed`, `EchoExpired`, `PingRefused`, `MoveSpent` (exit or bounce), `LevelWon`, `LevelLost`. The per-bat reveal sound is not an EventBus event: `BoardView.BatRevealed` fires as each bat's reveal begins and `GameRoot` plays the cue. Without a `SoundPlayer` on `GameRoot` the game logs an error and runs silent on `NullAudioService`. `EchoCave > Audio > Fill sound bank` fills a bank from `Audio/Sfx` by file name. UI sounds: `UiRoot` registers one `ClickEvent` handler on the panel root and plays the cue `UiSoundRules` picks from the pressed button's USS classes (`toggle` gives the toggle sound, `ping-button` none, anything else the click), and listens to `PopupsView.StarLit` to play the star sounds in step; it reaches the audio service through `GameRoot.Audio`. Music (D-035, ROK-189): `IAudioService.PlayMusic(MusicTrack)` makes a track the music; `AudioService` hands it to an optional `IMusicOutput` while the music switch is on, and with the switch off it only remembers the track (the switch fades the music out and, turned on again, brings the remembered track back). `MusicPlayer` (MonoBehaviour next to `SoundPlayer`) is the output: two looping `AudioSource`s that crossfade, the volume ramp being `MusicFade.Step` (pure, tested); it creates its sources on first use because `GameRoot` may ask for music before the player has woken up. `MusicBank` (ScriptableObject) has a clip and volume per `MusicTrack`, the menu track, the play playlist, `secondsPerTrack` (180) and `crossfadeSeconds`; `FindProblems()` and `ShippedMusicTests` (which also check the clips are Streaming and Vorbis) catch a missing clip. `MusicConductor` (plain C#, like `SoundCuePlayer`, built on enable by `GameRoot` from the bank on the music player) follows the flow: the menu track at the start and on `MenuOpened`, the first playlist track on the first `LevelStarted` or `LessonStarted`, then the next track every `secondsPerTrack` of play time (`GameRoot.Update` ticks it with unscaled time, so a paused game keeps its music and its count). A new level does not restart the track; going back to the menu resets the list. The four loops are made with RokertSfx's loop mode (`Audio/Music`, 12 s each). `EchoCave > Audio > Fill music bank` fills a bank from `Audio/Music` by file name. Without a `MusicPlayer` on `GameRoot` the game logs a warning and has no music.
- **Hints** (D-032): `HintPicker` (Core, pure) chooses the move a hint recommends: among the bats that can leave now, the one that frees the most others, ties to a visible bat and then the lowest id; it works on a copy of the board and uses no randomness. `EchoService.Pin(id)` keeps a bat revealed for the rest of the attempt, which is how a hinted hidden bat stays readable after the echo expires (`RevealedBatIds` is the echo's set plus the pinned ones). `IHintStock` / `HintStock` hold the player's hints in the save (one stock for the whole game, capped, publishing `HintsChanged`); `HintSettings` (ScriptableObject) has the starting count, the cap, hints per ad and `refillWithAds`. `GameFlow.RequestHint` (Playing and not paused) refuses visibly while a move animates, while the bat of the last hint is still on the board (`AlreadyHinted`) or when none are left (`HintRefused`, the bats shake, nothing is spent) and otherwise spends one, pins a hidden pick, calls `IBoardView.ShowHint` and publishes `HintUsed`. `BatView` pulses the hinted bat forever (a looping tween on a scale that multiplies the body and the arrow) until it is tapped or recycled. The HUD has a hint button next to the ping button (a smaller gold twin with a bulb icon from Penpot, a count badge, a ready and an empty state, and a shake when a hint is refused): `HudPresenter` shows the count from the start and follows `HintsChanged`, forwards the press to `GameRoot.RequestHint`, and shakes the button on `HintRefused`. `SoundCuePlayer` plays `Hint` on `HintUsed` and `Refuse` on `HintRefused`; `UiSoundRules` leaves the hint button without a click, like the ping button. The rewarded-ad refill (168-C): `GameFlow` exposes `CheckHint()` (a `HintStatus` with no side effects) through `IHintGate`, and `HintRefill` (plain C#, built by `GameRoot` because the root knows the ad service) sits between the button and the game: a press with hints goes straight to `RequestHint`; a press with none left (and `HintSettings.refillWithAds` on) shows `IAdService.ShowRewarded`, and only `Granted` grants `hintsPerAd` hints (capped by the stock) before asking for the hint as usual; a dismissed or unavailable ad grants nothing and the game refuses in the usual visible way. Busy, already-hinted and not-playing never offer an ad, and a second press while an ad is on screen does not stack another. With the refill on, the button with no hints shows an "AD" badge (`HintButtonState.WatchAd`) instead of looking dead. Free hints (D-033): `IHintRewardStrategy` (Core, pure) has two implementations, `StreakReward` (3 wins in a row with 3 stars on levels that never had 3 stars) and `DailyReward` (first launch of a new calendar day); each keeps one integer of state under a key and answers a `RewardMoment` (won, lost, day started) with the hints it earns. `HintRewardService` (Game, plain C#, built on enable by `GameRoot`) is the adapter from the game to those moments: wins come from `ProgressRecorder`, which reads the level's stars before saving, lost levels from the EventBus, the day from `IDayClock` (`SystemDayClock` over the local date); it pays through `IHintStock.GrantFree` (stock, then a one-hint reserve, then lost; the streak is on standby while `IHintStock.IsFull`, so it never earns a hint that would be lost), saves each strategy's state through `ISaveService.Get/SetRewardState` and publishes `HintRewarded`. `HintStock` publishes `HintReserveChanged`; the save is version 5 (`reserveHints`, `rewardState`). The HUD pops the hint button on `HintRewarded` and shows a "+1" tag while the reserve holds a spare; `SoundCuePlayer` plays `HintEarned`.
- **Tutorial** (D-034, in progress, ROK-181): `TutorialLesson` / `TutorialStep` (Core, pure) describe five lessons (a level, the steps, a free-hint flag); `TutorialRunner` (Core) follows the player through them and `TutorialValidator` checks a script. The save (version 6) has `tutorialSeen`; `TutorialSettings` (ScriptableObject) has `autoStart`. `GameFlow` has a tutorial mode (181-B): `RequestTutorial(thenStartGame)` starts the lessons from the menu, a level or a won or lost screen; `IsTutorial` swaps the catalog for the lessons, so `LevelIndex` counts lessons and `CurrentLevel` is the lesson's level. Lessons publish `LessonStarted`, `LessonWon` and `LessonLost` instead of the level events, so `ProgressRecorder`, the reward streak and the popups never see them (`SoundCuePlayer` plays the win and lose cues for them), and `TutorialChanged` tells the overlay about every step. `TutorialContinue` opens the next lesson or ends the tutorial (to level 1 on the first run, to the menu on a replay), `TutorialSkip` ends it at once, and `TutorialEnded(Completed | Skipped | Left)` makes `ProgressRecorder` save `tutorialSeen` (not for `Left`). `BoardPresenter` got a `CanTap` filter plus `BatTapped` and `TapRefused` events: a limited step refuses a tap on another bat and the bats shake (D-019). A lesson spends nothing from the hint stock: `CheckHint` answers `NotInLesson` (a visible refusal) in lessons without a hint and `Ready` in the hint lesson, so `HintRefill` never offers an ad there. The overlay (181-C, `UI/Tutorial`): `TutorialPresenter` (plain C#) listens to `TutorialChanged`, `LessonLost`, `TutorialEnded` and `MenuOpened` and drives an `ITutorialView` (bubble text, a Continue button reading "Got it", "Next" or "Done", Try again after a lost lesson, a ring on the focus) and forwards Continue, Retry and Skip through `ITutorialCommands` (`FlowTutorialCommands` adapts `GameFlow`). `TutorialView` (UI Toolkit, `Tutorial.uxml` and `Tutorial.uss`, an instance inside `hud-root` between the HUD and the popups, so the pause popup covers it) keeps a pulsing ring on the target every 33 ms: a bat through `ITutorialTargets` (`BoardTutorialTargets` turns `BoardView.TryGetBatWorld` into panel units with `RuntimePanelUtils.CameraTransformWorldToPanel`), or the ping or hint button through its `worldBound`. The layer ignores the pointer except for its buttons, so the board stays tappable; it carries the safe-area padding itself. The bubble sits under the HUD's top row (portrait and landscape offsets in the USS). The HUD shows lessons as "LESSON n / total" (`LessonStarted`, `SetLevelCaption`). The entry points (181-D): the five lessons are `DefaultTutorial` (Core, pure, tested as valid, solvable and playable through the real flow) written once into `TutorialLessonData` assets and a `TutorialCatalog` by `EchoCave > Tutorial > Create default lessons` (existing assets are kept, so tuning survives; `Validate lessons` and `ShippedTutorialTests` check them with `TutorialCatalog.FindProblems`). `GameRoot` takes the catalog and `TutorialSettings` (both optional) and builds the flow with the lessons; its `RequestPlay` is what the menu's Play button calls and starts the tutorial the first time (`TutorialEntry.ShouldAutoStart`: lessons exist, `autoStart` on, `tutorialSeen` false), with the first level following it. "How to play" is a button in the menu (`MenuPresenter` takes an optional `howToPlay` action) and in the pause popup (`PopupAction.HowToPlay`, `IPopupCommands.HowToPlay`); both start the tutorial with `RequestTutorial(thenStartGame: false)`, so it ends back in the menu, and the buttons only show when the game has lessons.
- **Challenges** (D-036, in progress, ROK-192; `Core/Challenges`, pure): `ChallengeMove` (a tap or a ping), `ChallengeAttempt` (id, moves, active seconds, attempts, solve time; not validated on construction), `ChallengeReplay.Verify` (replays an attempt through the real `MoveCommand` and says whether it cleared the level, in how many taps and with how many pings, or why it was rejected), `ChallengeScore` and `ChallengeRanking.RankOf` (taps, then seconds, then earlier solve) and `ChallengeDifficulty` (a seeded blind player's wasted taps and chance of a flawless run, shown in the Level Solver window). `ChallengeLevels` (the recipes, three so far, listed in `AllIds`: a spec and a seed, found with the difficulty metric; `SameLevel` compares two levels) and `EchoCave > Challenges > Create missing challenge assets` / `Check challenge assets` (editor) write and verify the `LevelData` copy in `Data/Challenges`, which keeps level id 0 because challenges are identified by their string id; the levels and how they were found are in `Docs/CHALLENGES.md`. The game mode (ROK-196): `GameFlow` has a challenge mode like the tutorial's (`RequestChallenge(index)` from the menu, `IsChallenge`, `CurrentChallengeId`, `ChallengeIndex`), built with an optional list of `ChallengeEntry` (id and level) that `ChallengeCatalogRules` validates at startup (valid and unique ids, valid and solvable levels, a move limit that fits the minimum). A `ChallengeRun` (Core) records every tap (`OnMoveExecuted`), every ping and the seconds on the board (`Tick`, not while paused); a win publishes `ChallengeSolved` with the built `ChallengeAttempt` (the solve time comes from an injected clock, `GameRoot` passes UTC now), running out of moves publishes `ChallengeFailed`, and `ChallengeStarted` (index, count, id, limit, pings, attempt) replaces `LevelStarted`, so `ProgressRecorder`, the reward streak and the level popups never see a challenge. A retry is a new run (attempt + 1); the menu, or starting the tutorial, ends the mode. `CheckHint` answers `NotInChallenge` and a request is refused visibly, so a challenge never spends from the stock or offers an ad. `ChallengeCatalog` (ScriptableObject, `Data/ChallengeCatalog.asset`, made, and later extended with new challenges at the end, by `EchoCave > Challenges > Create or update challenge catalog`) lists the challenges and holds `minSecondsPerTap`; `GameRoot` takes it (optional), frames the camera on `ChallengeStarted`, and builds a `ChallengeSelfCheck` (plain C#) that replays every solved attempt through `ChallengeReplay` and logs the verdict. The HUD shows "CHALLENGE n / total", the music and the sound cues treat a challenge as playing, and until the menu (192-E) the `GameRoot` context menu (`Challenges/Play the first challenge`, `Challenges/Back to the menu`) is the only way in. Results and screens (ROK-199, ROK-197): `ChallengeSelfCheck` now publishes its verdict as `ChallengeVerified`; `ChallengeRecorder` (plain C#) adds a saved try on every `ChallengeStarted` and, for a verdict that is valid, keeps the result through `ISaveService.RecordChallengeSolve` and publishes `ChallengeResultSaved` (rank among this device's results, new best, total tries). A rejected verdict is never kept. `ChallengeProgress` (Core, pure) holds the tries and the ten best `ChallengeResult`s of every challenge id, ordered by `ChallengeScore`; it is saved in version 7 of the save (`challenges`, each with its id, tries and results; versions 1 to 6 still read, entries with an invalid id or a nonsense result are skipped, `Reset` forgets them). `ChallengeAccess` (Core) opens the challenges when every numbered level has been won (`GameRoot.ChallengesUnlocked`, `ChallengeLevelsLeft`; `GameRoot.RequestChallenge` refuses while locked, the developer context menu does not). `IChallengeLeaderboard` is an edge service (registered in the `ServiceLocator`) with `Top(id, count)`: `LocalChallengeLeaderboard` reads the save, `NullChallengeLeaderboard` has nothing, and the online one (192-F) will replace the first. The menu has an optional "Challenges" button (`MenuView`, `IMenuView.ChallengesPressed`, hidden until `MenuPresenter` gets a `challenges` action); it hides the menu and `PopupsPresenter.OpenChallenges()` shows the list on the popup scrim: one card per challenge with its id, how it went ("Best: 52 taps in 2:20.5 (3 tries)", "Not tried yet"), the top three results and a Play button, dimmed with "Win n more levels to unlock" while locked. `PopupsPresenter` also shows the result popup on `ChallengeResultSaved` ("New best!" or "Challenge solved", the taps and time, the pings, the tries and the rank), "Not counted" with the reason when the replay rejected a solved board (so the player is never left on an empty board), and the lost popup on `ChallengeFailed`; Back (`PopupAction.CloseChallenges`) closes the list and `UiRoot` shows the menu again. The challenge popups are optional in `PopupsView` like the How to play button; the strings are in `ChallengeText` (pure) and the game is reached through `IChallengeSource` (`GameChallengeSource` adapts `GameRoot`). `ShippedUiTests` builds the real `Popups.uxml` and `Menu.uxml` into the real views.
- **Analytics** (D-037, ROK-207): `AnalyticsEvents` is the catalog of event and parameter names; `AnalyticsRecorder` (plain C#, created and disposed by `GameRoot`) listens to the EventBus (level start, win and lose by stable level id, pings and hints with where they happened, how the tutorial ended, the challenge flow) and calls `IAnalyticsService.Track`, catching a provider that throws. `LogAnalyticsService` writes each event as a log line (the editor and development builds); `NullAnalyticsService` counts nothing (release builds, until a provider is chosen).
- `GameRoot` (composition root of the Game scene): builds the flow from the catalog and the scene views, forwards `TapInput` taps, ticks the flow in `Update`, and re-frames the camera on `LevelStarted`. The game starts in the menu; the UI's Play button asks the flow to play. It registers the edge services in the `ServiceLocator` (`IAdService`, `ISaveService`, `IAudioService`, `IAnalyticsService`) and unregisters them in `OnDestroy`, using `Replace` because the registry outlives a Play session when Reload Domain is off.
- `ScreenAspect`: the single rule that says portrait or landscape (aspect >= 1 is landscape), shared by the backdrop art and the UI scaling.
- `IPointerBlocker` (`Game`, implemented in `UI`): `TapInput` asks it whether a pointer is over the UI and drops the tap if so.

## UI (EchoCave.UI, UI Toolkit, D-016 and D-021)

- **Stylesheets:** `Theme.uss` holds the Penpot palette as USS variables and the four Fredoka weights as `font-*` classes (static TTFs in `Art/Fonts`, OFL licence next to them). `Hud.uss` styles the HUD. Round buttons, the moves sign and the ping button are drawn with USS; only the icons are images.
- **MVP:** `IHudView` / `HudView` draw and forward the two buttons; `HudPresenter` (plain C#) listens to the `EventBus` (`LevelStarted`, `MoveSpent`, `PingUsed`, `EchoExpired`, `PingRefused`, `PauseChanged`, `MenuOpened`) and calls the game back through two delegates. `Dispose` unsubscribes everything.
- **Responsive:** `UiScaling` picks the reference canvas by orientation (1080x1920 matched to the width in portrait, 1920x1080 matched to the height in landscape) and `UiScale.PixelsPerUnit` gives the resulting scale; `ScreenInsets` turns `Screen.safeArea` into panel-unit padding. `UiRoot` applies both to a runtime copy of the `PanelSettings`, toggles the `portrait` / `landscape` class on the HUD, and re-applies when the screen size changes.
- **Input:** layout containers have `picking-mode: Ignore`, so only real controls catch a pointer. `UiPointerBlocker` implements `IPointerBlocker` with `panel.Pick`. The UI needs an `EventSystem` with the Input System UI module because the project uses only the new input backend.
- **Popups (D-022):** `Popups.uxml` is included in `Hud.uxml` as a template, so there is still one `UIDocument`; the dim layer inside it catches every pointer, so nothing behind a popup can be tapped. `IPopupsView` / `PopupsView` draw the Complete, Lost and Pause popups and forward their buttons as a `PopupAction`; `PopupsPresenter` (plain C#) picks the popup from `LevelWon`, `LevelLost`, `PauseChanged`, `LevelStarted` and `MenuOpened`, and answers the buttons through `IPopupCommands` (`FlowPopupCommands` adapts `GameFlow`). The popup hides the moment a button is pressed. The sound and music switches keep their state in the presenter and publish `AudioToggled`. The fade-in and the stars lighting up are USS transitions started by class changes; without a panel the final state is applied at once, which is what the tests see.
- **Main menu (D-023):** `Menu.uxml` is a second template in `Hud.uxml`, a sibling of the HUD root (the HUD is hidden while the menu shows). `IMenuView` / `MenuView` draw the logo and the Play button; `MenuPresenter` (plain C#) shows the menu on `MenuOpened` and hides it on `LevelStarted` or as soon as Play is pressed, then calls `RequestPlay`. It is told whether the flow is in the menu when the UI is built, because the flow publishes `MenuOpened` in its constructor, before anyone listens.
- **Shared controls:** `Controls.uss` holds the pill button (primary, secondary and large) and the switch, for every screen.
- `MovePathPlanner`: pure function from `MoveResult` + `GridLayout2D` to a `MovePlan` (start, target, bump point, travel in cells). All the animation geometry lives here so it is testable; the view only tweens between the points.
- `BoardCamera` + `CameraFraming`: orthographic framing of the board plus margin. Refits when the screen aspect changes (rotation, WebGL resize). The math is in `CameraFraming` for EditMode tests.
- `BoardBackdrop` (D-020): the layered night-cave background. It only reads the camera, so it also works in the menu. It owns a portrait set and a landscape set of five layers (base, far, motes, near, crystals) and shows the set that matches the camera aspect, not the platform. Each layer covers the view plus the margin its drift needs, and moves by depth from the pointer and a slow idle wander (mouse always; touch and pen only while pressed). The math lives in `Parallax` (pure, EditMode tests); tunables in `BackdropSettings`.
- Ping wave (D-028): `ShowPing` sends a `PingWave` (an expanding, fading ring built in code from the `Ping Ring` sprite, pooled with `ObjectPool<PingWave>` and a factory method, no prefab) from the centre of the board. Each revealed bat starts its fade after `EchoWaveTiming.DelayFor(distance in cells, wave speed)`; `ReachCells` is how far the ring must travel to cover the board. Both are pure and tested. Without a ring sprite on `BoardView` the bats reveal at once.
- Cell tiles: `BoardView` draws one tile sprite under every cell, reused between levels; scale and sorting order come from `BoardViewSettings`.
- `BoardViewSettings` (ScriptableObject): cell size, camera margin, fly speed, overshoot, bump/return timings, eases, the reveal and conceal fades and pop, and the ping wave speed, band share and sorting order. Distances are in cells.
- Cross-system notifications (level won, ping used, move spent) go through `EventBus` with readonly struct events.

## Patterns in use

| Need | Pattern | Where |
|---|---|---|
| Undoable moves (rewarded undo) | `IUndoableCommand` + `CommandHistory` | `MoveCommand` wraps `MoveResolver` result |
| Game flow | `StateMachine<T>` | Menu → Playing → Won / Lost |
| Ad provider | Strategy (`IAdService`) | AdMob, MAX, null provider for WebGL/editor |
| Echo behaviour | Strategy (`IEchoStrategy`) | `EchoService` |
| Bats and effects | `ObjectPool<T>` + Factory | `BatFactory`, `EffectFactory` |
| Edges (ads, audio, save, analytics) | Service Locator | registered once in the composition root |

Service Locator is not used inside the core: dependencies are constructor-injected. VContainer is deliberately deferred (see DECISIONS D-005).

## Levels as data

Levels are data assets (bat positions, directions, hidden flags, move limit, ping budget, star thresholds). An editor tool runs a solver over each level to (a) validate it is solvable and (b) compute the minimum move count, which feeds the star thresholds. CI-style EditMode test runs the solver over all shipped levels.

`LevelMetrics` (Core) measures a level's structure: bats, hidden bats, traps (bats blocked on the first move), waves (depth of the blocking chains) and a `Difficulty` heuristic. Since the minimum moves always equal the bat count (D-010), difficulty lives in those four numbers and in the move limit's slack. `LevelGenerator` (Core, with `SeededRandom` and `LevelSpec`) builds a level that matches a spec from a seed, deterministically, and keeps its difficulty in a window above the previous level's. It runs only in the editor: the `LevelGenerationPlan` asset (Editor assembly) holds one entry per level, and the Level Solver window writes the `LevelData` assets and fills the `LevelCatalog` from it (D-024).

## Level progression (v1, 10 levels)

1–3: no hidden bats, no move limit. 4–6: first hidden bat, generous pings. 7–10: more hidden bats, fewer pings; difficulty peak at 10.
